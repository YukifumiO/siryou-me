# Phase 9：自動化・監視

## 目的

データ取得からリスク判定、発注、約定確認、損益評価、自動停止までを一貫して自動化し、異常とモデル劣化を監視できる状態にする。

## 対象フロー

```text
データ取得
↓
品質・鮮度検査
↓
特徴量作成
↓
レジーム判定・AI推論
↓
リスク判定
↓
注文送信
↓
約定・口座照合
↓
損益・ドローダウン監視
↓
継続または自動停止
```

## 作業

### 1. ジョブ管理

- 各処理の依存関係を定義
- 成功・失敗・スキップの状態管理
- 冪等性の確保
- タイムアウトと再試行方針
- 失敗時の後続ジョブ停止
- 人間による承認が必要な操作の分離

### 2. 技術監視

- API応答率・遅延
- WebSocket接続状態
- DB接続とストレージ容量
- データの鮮度と欠損
- 特徴量計算時間
- モデル推論時間
- 注文応答時間
- 約定照合の不一致
- エラー率と連続失敗

### 3. モデル監視

- 入力特徴量の分布変化
- 欠損率と外れ値率
- 予測値・予測確率の分布
- 状態所属確率とレジーム頻度
- 確率校正の劣化
- 実現リターンに対する予測精度
- レジーム別のパフォーマンス
- 学習時の範囲外データの増加

### 4. 売買・リスク監視

- ポジションと口座残高
- 未約定注文
- 当日損益と累積損益
- 最大ドローダウン
- スプレッドとスリッページ
- リスク上限の残余
- 自動停止状態と理由
- 手動操作の監査ログ

### 5. アラート設計

重要度を区別する。

| レベル | 例 | 対応 |
|---|---|---|
| Info | ジョブ成功、日次レポート | 記録 |
| Warning | 軽度の遅延、ドリフト兆候 | 営業時間内に確認 |
| Critical | 発注状態不明、リスク上限、データ不正 | 即時停止・通知 |

### 6. モデル更新

- 更新頻度を事前に定義
- 新モデルは別バージョンとして検証
- 既存モデルとのチャンピオン・チャレンジャー比較
- 本番反映前の承認
- 即時ロールバック可能な状態
- 学習データ、コード、設定、依存環境の固定

### 7. 障害対応演習

- データソース停止
- 取引所API停止
- DB障害
- 認証情報の失効
- 二重発注の疑い
- 口座残高不一致
- 自動停止の発動
- モデルロールバック

## 完了条件

- [ ] データ取得から約定照合まで自動で稼働する
- [ ] 失敗時に後続処理が安全側で停止する
- [ ] データ、モデル、売買、リスクの監視がある
- [ ] Criticalアラートの通知が機能する
- [ ] 注文・ポジション・口座残高を照合できる
- [ ] モデルをロールバックできる
- [ ] 障害対応を別担当者が文書から実行できる

## 注意点

- 自動化は無監視化を意味しない。
- リスク制限や停止条件をモデルの予測で上書きしない。
- 自動再試行によって二重発注を起こさない。
