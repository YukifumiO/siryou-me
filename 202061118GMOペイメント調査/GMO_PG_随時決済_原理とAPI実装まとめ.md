# GMO PGマルチペイメントサービス：随時決済の原理・取消・返金・API実装まとめ

- 作成日：2026年11月18日
- 対象：GMOペイメントゲートウェイ「PGマルチペイメントサービス」
- 決済手段：クレジットカード、d払い（随時決済）、au PAY（auかんたん決済・随時決済）、ソフトバンクまとめて支払い（随時決済）
- 実装想定：PHP / Node.js・TypeScript、プロトコルタイプ（idPass）
- 資料の目的：まず**お金と取引状態の原理**を理解し、その後に決済手段ごとの制限とAPI設計を把握する。

> **この資料の読み方**：①原理 → ②事業者間のフロー → ③取消・返品 → ④各社仕様差 → ⑤API → ⑥実装・テスト。
> 「GMO公式仕様として確認できる事項」と「一般的な決済構造の説明／推定」を区別する。公開されていないキャリア内部DB・ネットワークの実装は断定しない。API名・必須パラメータ・契約条件は開発時点の最新版で必ず再照合する。

# 第1章　最初に理解する決済の原理

## 1. 決済成功と入金は別

利用者が1,000円を決済しても、GMO APIが「成功」を返した瞬間に加盟店の銀行口座へ1,000円が入るわけではない。

1. **決済承認／利用枠確保**：1,000円を支払えるか確認し、枠を確保する。
2. **売上確定**：加盟店が1,000円を請求対象として確定する。
3. **請求・精算**：カード会社またはキャリア側で請求データや資金精算が処理される。
4. **利用者からの支払／加盟店への入金**：それぞれの支払日・入金サイクルで実行される。

この4つは、発生時点も担当する事業者も異なる。

## 2. AUTH・SALES・CAPTUREとは

| GMOの区分 | 日本語 | 原理 | 利用者への請求 | 加盟店への入金 |
|---|---|---|---|---|
| `AUTH` | 仮売上 | 支払可否を判定して枠を確保する | 原則まだ売上請求を確定しない | まだ入金されない |
| `SALES` | 実売上 | 既存のAUTHを売上確定する | 請求・精算の対象になる | 入金は別途後日 |
| `CAPTURE` | 即時売上 | 承認と売上確定を一連の処理で行う | 請求・精算の対象になる | 入金は別途後日 |

```text
【2段階方式】
購入 → AUTH（1,000円確保） → 発送・サービス確定 → SALES（1,000円確定）

【即時売上方式】
購入 → CAPTURE（承認＋1,000円確定を一連の処理で行う）

どちらも売上確定後に請求・精算が進む。CAPTURE＝銀行口座への即時入金ではない。
```

※デビット・プリペイド等はAUTH時に利用者の残高が減少する場合があり、通常の後払いカードの説明をそのまま当てはめない。

## 3. AUTHを超えるSALESはできるのか

例：AUTHで1,000円を確保し、SALESで1,200円を売上確定したい。

- **カード**：単純な売上確定だけで無条件に増額できるわけではない。対応する金額変更・再与信の手続きを実施し、カード会社の承認が必要。再承認が失敗する場合もある。
- **d払い随時**：元の取引金額を超える増額は不可。減額済みの取引を元金額まで戻す機能には条件がある。
- **au随時**：増額不可。
- **ソフトバンク随時**：増額不可。

したがってシステム設計上、**キャリア決済のAUTH金額は原則その取引で確定できる金額の上限**として扱う。ただし減額の可否・条件は各社で違う。

# 第2章　GMOの外側で実際に何が起こるか

## 4. GMOの位置づけ

```text
利用者
  ↓ 注文・初回認証
加盟店のシステム（PHP / TypeScript）
  ↓ GMO API
GMO PG（取引受付、各社への接続、取引結果管理）
  ├─ カード系：アクワイアラ → 国際ブランドのネットワーク → イシュア
  └─ キャリア系：ドコモ系決済センター / KDDI / ソフトバンク系決済センター
```

- **加盟店**：注文やサービスの対価を請求する。
- **GMO**：加盟店向けAPIと事業者連携を提供する。契約構成により精算業務にも関わる。
- **カード・キャリア側**：本人確認・利用資格・利用枠・売上・返金等をそれぞれのルールで処理する。

## 5. クレジットカード：AUTHの裏側

```text
加盟店 --AUTH 1,000円--> GMO
  --> アクワイアラ／カードネットワーク --> イシュア（カード発行会社）
  <-- 承認/否認 -----------------------------------------------------
```

イシュアはカード状態、利用可能枠、不正利用リスク等を確認する。承認すれば原則として1,000円分の与信枠を確保する。概念例：利用可能枠10万円 → 9万9,000円。ただし実際の内部テーブルや保留管理の方法は発行会社ごとに異なる。

**3Dセキュア2.0は本人認証であり、AUTHの与信承認とは別の処理**。本人認証成功でも与信が否認されることがある。

## 6. クレジットカード：SALESの裏側

```text
加盟店 → GMO：SALES
  ↓
アクワイアラ等で売上を確定・送信対象にする
  ↓
クリアリング：加盟店側と発行会社側が取引明細を交換・照合
  ↓
セトルメント：関係金融機関の間で差引精算
  ↓
利用者のカード請求／加盟店への入金（それぞれのサイクル）
```

- **クリアリング**：元承認・加盟店・金額・日付等の売上データをやり取りする。
- **セトルメント**：売上・返金等を集計して関係者間の差額を精算する。
- `SALES` 成功＝カード会員の口座から引落済み、ではない。

カードの`CAPTURE`はAUTHとSALESを一連の操作で実行するが、後続のクリアリングや精算そのものを省略する意味ではない。

## 7. キャリア決済：初回の「利用承諾」と個別の「課金」は別

**初回利用承諾**

```text
利用者がキャリア決済を選択
 → 加盟店 → GMO → キャリア側の承諾画面
 → dアカウント / au ID / ソフトバンク側の認証・承諾
 → 結果確認・承諾番号を加盟店側で管理
```

この段階で、一般に個別商品1,000円の売上が自動発生するわけではない。

**2回目以降の随時課金**

```text
加盟店が注文ID・金額・承諾番号等を使って課金要求
 → GMO → キャリア側で承諾有効性・利用条件・上限等を確認
 → AUTHまたはCAPTUREの結果を返す
 → AUTHの場合は後日SALES
 → キャリア側の利用者請求・加盟店精算へ
```

初回の承諾に成功していても、解約、利用停止、上限超過等で後続課金が失敗し得る。

## 8. キャリアのAUTH・SALESの中身

- `AUTH`：キャリア側の決済利用枠を確保する状態。内部で「残枠を直接減算」するのか「保留取引を集計」するのか等のデータ構造は公開されていない。
- `SALES`：キャリア側へ売上確定を要求し、請求対象とする。利用者への請求形態は電話料金合算・カード・残高等によって異なる。
- `CAPTURE`：初回の決済要求で売上確定まで実施する。加盟店への即時入金を意味しない。

**注意すべき実例：auはAUTH成功後のSALESであっても、回線解約・料金停止・督促等により失敗する場合がある**。AUTHは将来の売上成功を無条件に保証しない。

キャリア別の利用者側の支払原資が異なることも重要である。例えばauかんたん決済では、電話料金合算払いとクレジットカード払いで**SALES時の減額の可否が違う**。そのため、同じ「キャリア決済」という名前でも内部の後続処理は同一ではない。

# 第3章　キャンセル・返金の原理（3種類）

## 9. キャンセルの3分類

| 分類 | 元の状態 | 原理 | 1,000円の例 |
|---|---|---|---|
| **① 仮売上取消** | AUTH | 確保枠を解除。通常は未確定売上なので返金ではない | AUTH 1,000円 → 確保解除 |
| **② 売上確定後の取消** | SALES / CAPTURE | 確定済み売上を相殺・取消し、請求対象から除外する処理 | SALES 1,000円 → 取消 |
| **③ 請求確定後の返品・返金** | SALES / CAPTURE | 既に進んだ請求・精算に対し返金・後続調整 | 11月売上1,000円 → 12月返金 |

①は「売上を作らない」、②は「確定した売上を取り消す」、③は「確定・請求処理が進んだ売上を調整する」という違い。

**重要：これは原理的な分類であり、GMO APIが常に3本に分かれるわけではない。** 同じ取消APIが状態・日付によって異なる扱いになることもある。

## 10. なぜ月跨ぎで違いが出るのか

売上は事業者ごとの締め処理に組み込まれ、利用者請求や事業者間精算に進む。元の月の請求処理が進むと、「元売上の取消」ではなく「翌月以降の返金・精算調整」が必要になることがある。

```text
11/10 売上確定 1,000円
11/20 取消      → 決済方式によっては当月取消
12/05 返金      → 決済方式によっては月跨ぎ返品
```

ただし**暦上の月跨ぎ＝銀行送金済みとは限らない**。GMOの取引区分、キャリアの請求締め日、加盟店入金日が一致するとは限らない。

## 11. 一部キャンセル・減額は3つの意味を分ける

1. **仮売上から実売上へ移るときの減額**：AUTH 1,000円 → SALES 800円（元の1,000円全体を返金するのではなく、売上を800円で確定）。
2. **売上確定後の一部取消**：確定売上1,000円 → 300円分を取り消して実質700円とする。
3. **売上確定後の一部返品・返金**：請求・精算が進んだ1,000円に対し300円の返金・請求調整をする。

この3つをすべて「一部キャンセル」と呼ぶと仕様を誤解しやすい。API設計では分けて扱う。

## 12. 「利用承諾終了」は返金ではない

キャリア随時決済の**承諾を終了**しても、過去に確定した売上は自動的に返金されない。今後の新規随時課金を止める処理と、既存取引の取消・返金は別物である。承諾終了後も、期限内なら既存取引に対する実売上・取消等が可能な場合がある。

# 第4章　4種類の決済手段の仕様比較

## 13. 一部返金と減額の可否（GMO経由の随時決済）

| 決済手段 | AUTH中の一部取消 | AUTH→SALES時の減額 | SALES/CAPTURE後の一部返金 | 特徴 |
|---|---|---|---|---|
| クレジットカード | 単純な「部分取消」とは別に金額変更・再与信等 | 条件付きで対応 | 金額変更・返品等の条件に従う | カード会社の承認と取引区分が重要 |
| d払い | 取消自体は全額 | AUTH額より少額でSALES可能 | **可能、残額0円まで複数回** | 支払方法によって一部返金が失敗することあり |
| auかんたん決済 | 全額のみ | **電話料金合算：可能／カード払い：不可** | **可能、再返金に制限** | 当月取消と翌月以降の返品を区別 |
| ソフトバンク | 全額取消 | **1回のみ減額可能** | **GMO経由では不可** | SALES/CAPTURE後は全額取消が基本 |

※カードの後日減額は、単純に「確定売上に対して一部返金APIを何回も実行できる」とは限らない。適用可能な変更方法・元取引の状態・カードブランド等を確認する。

## 14. d払い（随時決済）

- **AUTH後のSALES期限**：取引当日（取引の3秒後）～翌々月末20時。
- **AUTHの取消**：全額のみ。取引当日3秒後～翌々月末20時。
- **SALESの取消・一部返金**：実売上当日1分後～仮売上日から179日後の20時。
- **CAPTUREの取消・一部返金**：即時売上当日1分後～即時売上日から179日後の20時。
- **一部返金**：残額が0円になるまで複数回可能。ただし支払方法によって失敗する場合あり。
- **増額**：元の金額を超える増額不可。減額済み取引を元金額まで戻す操作には条件あり。
- **日付の注意**：20時以降の処理が翌日扱いになる等、独自の判定ルールがある。

公式：https://docs.gmo-pg.com/mulpay/docs/payment-method/wallet/dbarai/accept/overview

## 15. auかんたん決済（随時決済）

- **AUTH後のSALES期限**：仮売上後90日以内。AUTH成功後でも契約状態等の変化でSALES失敗あり。
- **AUTHの取消**：仮売上後90日以内、全額のみ。
- **SALES/CAPTUREの当月取消**：売上確定した月内。全額または一部。GMO上は`CANCEL`。
- **SALES/CAPTUREの翌月以降の返品**：売上確定翌月～翌々月末。全額または一部。GMO上は`RETURN`。
- **一部返金後の再返金**：不可。
- **AUTH→SALES時の減額**：電話料金合算払いは可能、クレジットカード払いでは不可。
- **増額**：不可。

例：11月10日に即時売上 → 11月中は当月取消の扱い、12月1日～翌年1月31日は返品の扱い。ただし実取引の条件も確認する。

公式：https://docs.gmo-pg.com/mulpay/docs/payment-method/wallet/au/accept/overview

## 16. ソフトバンクまとめて支払い（随時決済）

- **AUTH後のSALES期限**：仮売上後60日以内。
- **AUTHの取消**：仮売上後60日以内。
- **SALES/CAPTURE後の全額取消**：売上確定日を含む180日以内。
- **取消回数**：原則1取引1回。
- **減額**：AUTH→SALESに移る際に一度のみ可能。
- **売上確定後の一部返金**：GMOの随時決済仕様では提供なし。
- **増額**：不可。

公式：https://docs.gmo-pg.com/mulpay/docs/payment-method/wallet/sb/accept/overview

## 17. クレジットカード

- `AUTH`：与信枠を確保。オーソリ有効期間はカードブランド・契約・取引条件に依存。
- `SALES`：AUTH取引を実売上へ変更。
- `CAPTURE`：即時売上。
- `VOID`、`RETURN`、`RETURNX`などの区分を使い、取消／返品の条件が異なる。
- `ChangeTran`等で金額変更が可能な場合があるが、増額は再与信や新たな承認が必要になる。単純にAUTHより大きな金額をSALESで指定すればよいわけではない。
- **月跨ぎ**：カードでは月跨返品として`RETURNX`を使う場面があるが、元の売上状態・カード契約・GMO仕様を見て判断する。
- **3Dセキュア**：本人認証であり与信承認とは別。カード保存はGMOのトークン化機能を使用する。

公式：https://docs.gmo-pg.com/mulpay/docs/payment-method/credit/card/overview

## 18. 各社の返金の違いはキャリアの内部仕様なのか

**確認できたこと**：GMOを経由した決済で、各キャリアの一部返金回数・減額可能時点・返金期限が違う。auでは利用者の支払方法によってSALES時の減額の可否も異なる。

**未確定のこと**：制限のすべてがキャリア自身の必須仕様なのか、GMOとキャリアの接続契約・APIの制約なのか。各社の非公開DB構造や請求エンジンの実装を直接確認できない。

**妥当な仮説（断定しない）**：請求締め・精算、残高・カード払い等の支払原資の違い、返金履歴の管理方法、事業者間APIの仕様、リスク管理などが制限に影響する可能性がある。特にソフトバンクの「売上確定後の一部返金不可」を内部DBの機能不足と決めつけない。

# 第5章　GMOのAPIと実装フロー

## 19. API方式

- 今回の4手段をそろえる場合、**プロトコルタイプ idPass**が検討しやすい。
- GMOにはOpenAPIタイプもあるが、決済方法や個別機能の対応範囲は同一ではない。
- idPassは原則`/payment/{API名}.idPass`にフォームエンコードで送信する。日本語などの文字コードは各API仕様に従う。JSON APIとは異なる。
- テスト接続先の一例：`https://pt01.mul-pay.jp`（実際の指定ホストを優先）。

公式入口：https://docs.gmo-pg.com/mulpay/

## 20. 初回登録・承諾と後続課金のAPI

| 手段 | 初回処理 | 2回目以降の課金 |
|---|---|---|
| カード | `SaveMember` / `SaveCard`（MpToken.js等でカード情報をトークン化） | `EntryTran` → `ExecTran`（3DS等の必要処理を含む） |
| d払い | `EntryTranDocomoAccept` → `ExecTranDocomoAccept` → 利用者承諾画面・結果確認 | `EntryTranDocomo` → `ExecTranDocomo` |
| au | `EntryTranAuAccept` → `ExecTranAuAccept` → 利用者承諾画面・結果確認 | `EntryTranAu` → `ExecTranAu` |
| ソフトバンク | `EntryTranSbAccept` → `ExecTranSbAccept` → 利用者承諾画面・結果確認 | `EntryTranSb` → `ExecTranSb` |

**注意**：承諾の取引登録・実行APIの成功だけで「利用者の承諾完了」と判定しない。必要な画面遷移、結果通知・照会、承諾番号保存まで実装する。

## 21. キャンセル・照会のAPI

| 手段 | 取消・返品 | 取引照会 |
|---|---|---|
| カード | `AlterTran`（`VOID` / `RETURN` / `RETURNX`など）、金額変更は`ChangeTran`等 | `SearchTrade` |
| d払い | `DocomoCancelReturn` | `SearchTradeMulti`等。承諾状態照会は別API |
| au | `AuCancelReturn` | `SearchTradeMulti`等。承諾状態照会は別API |
| ソフトバンク | `SbCancel` | `SearchTradeMulti`等。承諾状態照会は別API |

API一覧：

- カード：https://docs.gmo-pg.com/mulpay/docs/payment-method/credit/card/api-list
- d払い：https://docs.gmo-pg.com/mulpay/docs/payment-method/wallet/dbarai/accept/api-list
- au：https://docs.gmo-pg.com/mulpay/docs/payment-method/wallet/au/accept/api-list
- ソフトバンク：https://docs.gmo-pg.com/mulpay/docs/payment-method/wallet/sb/accept/api-list
- idPass全体：https://docs.gmo-pg.com/mulpay/apis/protocol-type/idpass

API一覧・リファレンスで要求・応答項目を必ず照合する。特に金額や取消区分のパラメータは**支払方法によって違い、共通化してよいとは限らない**。

## 22. 取消処理の共通フロー

```text
[利用者/管理者の取消要求]
            ↓
[自社DBの注文・決済・過去の返金を確認]
            ↓
[GMO取引照会：現在の取引状態、金額、決済日]
            ↓
[決済方法ごとの判定]
 ├─ AUTHか / SALES・CAPTUREか
 ├─ 全額か / 一部か
 ├─ 当月か / 翌月以降か
 ├─ 返金期限・回数の条件を満たすか
 └─ 同一注文で取消処理中でないか
            ↓
[適切なGMO API実行]
            ↓
[結果照会・通知で最終状態確認]
            ↓
[自社DBの返金履歴・残額・注文状態を更新]
```

**タイムアウト時は失敗と決めつけて再送しない。** GMO側で既に取消成功している可能性があるため、同じ注文・取引を照会してから対処する。

# 第6章　PHP / Node.js・TypeScriptでの設計

## 23. 推奨するモジュール構成

```text
payment/
  GmoClient                 # HTTP送受信・認証情報・レスポンス解析
  CardPayment               # カード登録・3DS・AUTH/SALES/CAPTURE
  DocomoPayment             # 承諾・課金・返金
  AuPayment                 # 承諾・課金・返金
  SoftbankPayment           # 承諾・課金・返金
  PaymentInquiry            # 状態照会
  PaymentCancel             # 返金の可否判定・API選択
  PaymentRepository         # DB操作
  NotificationHandler       # 結果通知の検証・反映
```

- PHPではcURL等、Node.js/TypeScriptでは`fetch`等で通信できる。
- idPassはフォーム形式であり、JSONと混同しない。文字コード（Windows-31J等）は公式仕様を確認して適切にエンコード・デコードする。
- ショップID/パスワードとサイトID/パスワードの使い分けに注意する。決済系APIと会員管理APIで必要な認証情報が違う。
- `MpToken.js`などを使い、加盟店サーバーでカード番号・セキュリティコードを直接保持しない。
- 本番は本人認証（3Dセキュア2.0）、署名・通知検証、権限、監査ログ、冪等性、再照会まで含める。

## 24. TypeScriptの業務モデル例

以下はGMO APIのリクエスト仕様そのものではなく、**自社システム内の設計イメージ**。

```typescript
type PaymentMethod = "card" | "docomo" | "au" | "softbank";
type ConsentStatus = "PENDING" | "ACTIVE" | "ENDED" | "EXPIRED";
type TransactionStatus =
  | "UNPROCESSED" | "AUTH" | "SALES" | "CAPTURE"
  | "CANCEL" | "RETURN" | "FAILED";

type RefundDecision =
  | { allowed: true; operation: "AUTH_CANCEL" | "SALES_CANCEL" | "RETURN" | "REDUCE_BEFORE_SALES" }
  | { allowed: false; reason: string };

interface PaymentTransaction {
  orderId: string;             // GMOに渡す一意なID
  paymentMethod: PaymentMethod;
  status: TransactionStatus;
  originalAmount: number;
  currentAmount: number;
  authorizedAt?: string;
  capturedAt?: string;
  refundedTotal: number;
}
```

## 25. 最低限必要なDB情報

**決済手段（payment_methods）**：自社会員ID、手段、GMO会員ID・カード連番またはキャリア承諾番号、承諾状態、有効期限等。

**決済取引（payment_transactions）**：注文ID、手段、元金額、現在金額、AUTH日時、SALES/CAPTURE日時、GMO取引識別情報、取引状態等。

**返金履歴（refunds）**：返金ID、元取引、返金要求額、成功額、返金日時、実行状態、照会履歴等。

認証・取引用の機密情報は暗号化・権限制限。カード番号・セキュリティコードを保存しない。

## 26. 開発の順番

1. GMOテスト環境とカード・キャリア3社の契約／有効化を確認。
2. 共通HTTPクライアントで接続確認。
3. カード登録・3DS・AUTH/SALES/CAPTURE・取消／照会を実装。

## 1ページでの要約

> **AUTH**＝支払枠を確保。原則、売上確定前。
>
> **SALES**＝AUTHを売上確定。後続の請求・精算へ。
>
> **CAPTURE**＝承認と売上確定を一連の処理で行う。
>
> **キャンセルの3原理**＝①AUTHの枠解放、②確定売上の取消、③請求・精算が進んだ売上の返品・返金。
>
> **一部返金**＝d払いは複数回対応、auは対応するが回数と月跨ぎの条件あり、ソフトバンクは売上確定後の一部返金非対応（GMO経由）。カードは金額変更・返品区分等の個別条件で判断。
>
> **最重要の設計方針**＝「初回承諾」「AUTH/SALES/CAPTUREの取引状態」「請求・入金」「返金履歴」を別に管理し、取消前後は必ず取引照会する。
